Cómo está construida la app: tecnologías, capas, cómo viajan los datos y dónde vive cada cosa. El detalle de las tablas está en el modelo de datos.

Capas

Navegador · ReactPáginas (pages/) armadas con componentes (components/, components/common/), hooks y contextos (sesión, avisos, datos sin guardar)
↓
services/api.js · única capa de datos del frontendNinguna página usa fetch ni localStorage directamente
↓ con servidor  ·  sin servidor ↘ localStorage del navegador
Express · app.jsSesión (token), permisos de cada ruta (permisos.js), hosts permitidos, errores sin detalles
↓
Rutas · routes/Solo traducen HTTP ↔ DAO con responder(); no tienen SQL
↓
DAO · dao/Compras, filas, catálogo y usuarios: validan, escriben en transacción y lanzan ErrorDatos
↓
SQLite · depanas.dbModo WAL, claves foráneas, migraciones al abrir

shared/ guarda las reglas de negocio puras: validar compras, IVA, archivo, gastos, usuarios, productos y respaldos. Las usan igual el backend y el modo local del frontend, así las dos versiones nunca se separan.

Dos modos que nunca se mezclan

Al cargar, api.js pregunta una vez a /api/health si hay servidor.

ModoDónde quedan los datosSeguridad
Servidor (el del cliente)SQLite, en depanas.dbReal: sesión con token y permisos en cada petición
Local (sin backend)localStorage del navegadorSolo una barrera de interfaz

Si el servidor falla, el error se muestra; nunca se guarda en silencio en el navegador.

API del servidor

Toda la API exige sesión (Authorization: Bearer), salvo /api/health y entrar.

RutaQué hace
POST/DELETE /api/sesionEntrar (devuelve el token) y salir
GET /api/comprasCompras con filtros (proveedor, artículo, fechas)
POST /api/compras, GET/PUT/DELETE /api/compras/:idCrear, ver, editar y eliminar una compra
POST /api/compras/eliminarVarias compras a la vez (casillas)
/api/catalogo y /api/catalogo/:tipo/…Leer, agregar, renombrar, eliminar e importar el catálogo; asignar categoría y productos a un artículo
/api/usuarios, /api/requisitos-contrasenaGestor de usuarios (solo el administrador)
/api/db/exportar(-json), /api/db/importar(-json)Respaldos: base completa y compras en JSON
/api/apagar, /api/pestanasSolo en la versión .zip: apagar y cerrar con la última pestaña

Programación orientada a objetos

El proyecto está en JavaScript. Usamos los principios de POO donde aportan, sin forzar clases donde React y Express trabajan mejor con funciones:

PrincipioDónde
EncapsulamientoCada DAO (comprasDAO(db), catalogoDAO(db)…) es un objeto que guarda la conexión y expone solo sus operaciones. El SQL, las transacciones y las reglas quedan adentro. Lo mismo hacen las sesiones (crearSesiones()) y las pestañas.
HerenciaErrorDatos (dao/errores.js) es una clase que hereda de Error y suma el código HTTP y el campo del formulario.
Abstracciónservices/api.js esconde si los datos van al servidor o al navegador: las pantallas piden «guarda esta compra» sin saber cómo.
Polimorfismoresponder() trata igual cualquier ErrorDatos (400, 403, 404 o 409) y cualquier otro error; las mismas funciones de api.js se comportan distinto en cada modo.
ComposiciónCada pantalla se arma con piezas de components/common/ (Boton, Campo, Tarjeta, Modal…).

Dónde vive cada cosa

frontend/src/
  pages/              las pantallas (AgregarCompra, PantallaMaestra, PantallaCatalogo…)
  components/         piezas de las pantallas; common/ = la UI base
  context/            sesión, avisos (toasts), datos sin guardar
  services/api.js     única capa de datos (servidor o local)
  utils/              formato, exportar (Excel/JSON), mensajes.js (todos los textos)
  styles/             tokens de la marca, collage, movimiento
backend/
  app.js              Express: sesión, permisos, errores
  routes/             HTTP ↔ DAO
  dao/                acceso a datos (patrón DAO) y ErrorDatos
  db.js · db/         conexión, esquema, migraciones, catálogo inicial y datos demo
  test/               pruebas con node:test
shared/               reglas que usan igual backend y frontend
desktop/              la versión .zip para Windows
docs/                 esta documentación, el manual y los documentos técnicos

Cada carpeta de frontend/src/ tiene su propio README.md con sus convenciones.
