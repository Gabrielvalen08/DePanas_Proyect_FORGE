# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Proyecto

App web de contabilidad para el restaurante **De Panas SV**: registro de compras e insumos y, más adelante, costos, gastos y márgenes. Es un proyecto académico de POO. Los requisitos y el descubrimiento están en los PDF de la raíz (`Documento de requerimientos - De Panas.pdf`, `Documento de descubrimiento - De Panas.pdf`).

Hay un **frontend** (`frontend/`) y un **backend** (`backend/`): Node.js + Express con SQLite (`node:sqlite`, Node ≥ 22.13) en `http://localhost:3000`, que escucha **solo en `127.0.0.1`** (`HOST=0.0.0.0` lo abre a la red; no recomendado). El frontend funciona también sin backend (modo local, ver abajo). Para el cliente se entrega un **.zip para Windows** (`desktop/`) con los dos adentro y el Node.js oficial, que se usa en el navegador como sitio web local (`http://localhost:4510`); la guía de instalación del cliente está en `docs/INSTALACION_CLIENTE.md`.

## Comandos

### Backend (desde `backend/`)

- `npm install`, `npm start` (o `npm run dev` con recarga). La base vive en `backend/db/depanas.db` (ignorada por git).
- `npm test`: tests con el runner nativo (`node --test`); cada test usa una base temporal. Importa `test/ayudantes.js` antes que `app.js`: baja las iteraciones del hash (`DEPANAS_ITERACIONES_HASH`) e inicia sesión (`entrar(base)`, `cabeceras(url)`), porque toda la API exige sesión. `test/seguridad.test.js` prueba sesión, permisos, bloqueo y recálculo del hash.

### Versión .zip para el cliente (desde `desktop/`, en Windows)

- `npm install`, `npm run preparar` (arma `salida/De Panas SV/`), `npm run dist` (además `dist/De Panas SV <versión>.zip`) y `npm run test:escritorio` (Playwright sobre la carpeta armada: abre el `.cmd` de verdad). La carpeta lleva `Abrir De Panas SV.cmd`, `node/node.exe` (el **Node.js oficial sin modificar**, firmado por OpenJS Foundation; `preparar.mjs` comprueba la firma) y `app/` (`iniciar.mjs`, `servidor.mjs`, backend, shared, frontend compilado y `node_modules`). Es un **sitio web local**: `iniciar.mjs` arranca `servidor.mjs` oculto (`crearApp` en `http://localhost:4510`, en `127.0.0.1` y `::1`, con `estaticos`, `hostsPermitidos` y `apagar`), abre el navegador predeterminado y crea un acceso directo en el escritorio. Se apaga con **«Apagar De Panas SV»** del menú (`POST /api/apagar`, solo si `/api/health` dice `apagable`) o al cerrar la última pestaña con sesión (`backend/pestanas.js`, ver Arquitectura); en esta versión no hay «Cerrar sesión». La base va en `%APPDATA%\De Panas SV\depanas.db`. **No es un `.exe` propio** porque Smart App Control bloquea los ejecutables sin firma; un `.cmd` o `.lnk` marcado como descargado de internet también se bloquea, así que el cliente **desbloquea el .zip** (Propiedades → «Desbloquear») antes de extraerlo. Variables solo para pruebas: `DEPANAS_DATOS`, `DEPANAS_PUERTO` y `DEPANAS_PRUEBA=1`. **Demostración:** `Abrir De Panas SV (demo).cmd` (`DEPANAS_DEMO=1`) abre otra instancia en el puerto 4511 con datos en `%APPDATA%\De Panas SV\demo`, que arranca con dos meses de compras de ejemplo (`backend/db/compras-demo.json`, generado por `npm run demo:generar` con semilla fija; `backend/db/demo.js` solo lo carga en una base sin compras). También: `npm run demo:base` crea `backend/db/depanas-demo.db`, y el JSON se puede cargar desde Cargar datos. Pruebas: `backend/test/demo.test.js`. Detalles en `desktop/README.md`.

### Frontend (desde `frontend/`)

- `npm install`: instala las dependencias
- `npm run dev`: servidor de desarrollo Vite en http://localhost:5173 (redirige `/api` a `localhost:3000`)
- `npm run build`: build de producción en `frontend/dist/`
- `npm run preview`: sirve el build
- `npm run lint`: ESLint 9 con `jsx-a11y` (strict) y `react-hooks` v7. Prohíbe `style={{}}`
- `npm run test`: Vitest en modo watch; `npm run test:run` una sola vez (`testTimeout` de 15 s en `vite.config.js` y `asyncUtilTimeout` de 5 s para `findBy…`/`waitFor` en `src/test/setup.js`: con todas las suites en paralelo una prueba de ~0,6 s puede pasar de 5 s). Las pruebas leen los `.xlsx` con `read-excel-file` (`/universal` en Vitest, `/node` en e2e)
- Un solo archivo de test: `npx vitest run src/pages/AgregarCompra.test.jsx`
- `npm run test:e2e`: pruebas end-to-end con Playwright (`e2e/`, config en `playwright.config.js`). Levantan su propio backend (puerto 3100, base temporal `e2e/.tmp/e2e.db` vía `DEPANAS_DB`) y Vite (5174, `DEPANAS_API`; si un puerto está ocupado, `E2E_PUERTO_BACKEND` y `E2E_PUERTO_FRONTEND` lo cambian), así que no tocan `depanas.db` y conviven con `npm run dev`. Proyectos `escritorio` y `movil` (Pixel 7). `e2e/aviso-salida.spec.js` corre en los dos proyectos. `e2e/ayudantes.js` hace fallar una prueba si la página lanza una excepción, escribe un error en consola o el backend responde 5xx. La primera vez: `npm install` (trae `@playwright/test`) y `npx playwright install chromium`. Ayudantes: `entrar`, `menu`, `confirmar(page, etiqueta)` y `salir(page)`. `--headed` para ver el navegador, `npm run test:e2e:ui` para el modo interactivo y `npx playwright show-report` para el reporte con capturas, video y trace de lo que falló. Una pantalla o un flujo nuevo lleva su prueba en `e2e/`; los textos se importan de `src/utils/mensajes.js`.

`react-hooks` v7 rechaza `setState` síncrono dentro de `useEffect`: actualiza estado desde callbacks o promesas (ver la carga en `PantallaMaestra.jsx`).

## Arquitectura

React 18 + Vite 5 + react-router-dom 6, en JavaScript (JSX) sin TypeScript. Íconos: solo `lucide-react`.

- `src/main.jsx` monta un **router de datos** (`createBrowserRouter` con una sola ruta `*` → `App`, que sigue usando `<Routes>`; `useBlocker` lo exige) y `<MotionConfig reducedMotion="user">`, y carga `styles/global.css`. En pruebas de `App`, `createMemoryRouter` + `RouterProvider`. `src/App.jsx` define el layout (`Sidebar` en escritorio, `BarraInferior` en móvil) y las rutas: `/` → `AgregarCompra` (página principal: una o varias compras, cada una en un `BloqueCompra` con su propio guardar), `/compras` → `PantallaMaestra` (tabla de listas activas, filtros en línea con `FiltrosEnLinea`, detalle en `DetalleLista` para ver, editar y eliminar, y **casillas como en el correo**: una por compra a la izquierda y «Elegir todas» en el encabezado, que elige la página y un aviso ofrece elegir todas las de la lista; la fila elegida cambia de color y aparece el ícono Eliminar junto al de Filtrar; solo «Agregar compra» lleva texto; el ⋮ lleva Exportar y Cargar; con más de 50 compras va por **páginas de 50** (`TAM_PAGINA`), con «1–50 de 380» y flechas arriba, como en el correo; la paginación es en el cliente: la API sigue devolviendo todas las compras filtradas). `/catalogo` y `/catalogo/:seccion` → `PantallaCatalogo` (proveedores, categorías, materiales o productos; editor en `EditorCatalogo`, donde una categoría o un producto también eligen sus materiales; `/configuracion/*` redirige aquí), `/exportar` → `PantallaExportar` (rango de fechas + Excel .xlsx o JSON), `/cargar` → `PantallaCargar` (elige compras de un JSON exportado; las modificadas se comparan en `CompararCompra`), `/usuarios` → `PantallaUsuarios` (Gestor de usuarios; editor en `EditorUsuario`). `/agregar-compra` redirige a `/` y cualquier otra ruta a la pantalla de inicio del usuario. Las rutas, íconos y títulos viven en `components/navegacion.js` (Catálogo va en `itemsNavegacion`, debajo de Lista de compras; `itemsPie` = Gestor de usuarios, al pie del menú, arriba de Cerrar sesión; Exportar y Cargar datos llevan `oculto: true`: siguen siendo rutas con permiso pero no salen en el menú; se abren desde el ⋮ de Lista de compras y su `Header` lleva Regresar con `useRegresar('/compras')`). En móvil, `BarraInferior` muestra solo los ítems con `enBarra` (Agregar, Lista, Catálogo) y un botón **Más** que abre una hoja con el resto (Usuarios) y Cerrar sesión.
- **Aviso antes de perder datos** (`context/DatosSinGuardarContext.jsx`, `components/AvisoSalida.jsx`, textos en `AVISO_SALIDA`): un solo `useBlocker`, en `DatosSinGuardarProvider`, dentro de `App`. Cada formulario declara `useDatosSinGuardar({ sucio, registrar, cierreRef })` (sin provider no hace nada); `registrar` arranca su flujo normal (validación y «¿Guardamos…?») y el hook devuelve `terminar(ok)`, `aceptar()`, `cerrar()` y `descartar()` para contar cómo acabó. El aviso ofrece «Salir sin guardar» y «Registrar» (sin `registrar`, como en Exportar, «Seguir aquí»); la X y Esc solo lo cierran. Con varios bloques, «Registrar» guarda uno y el aviso vuelve. Lo dispara: cambiar de pantalla (menú, barra, Regresar, Atrás), cerrar una ventana con X/Esc/clic fuera (`useCierreConAviso`; Cancelar conserva su confirmación), Cerrar sesión y Apagar antes de su confirmación (`usePedirSalida`), y recargar o cerrar la pestaña (`beforeunload`, ventana genérica del navegador: no admite texto propio). **Formulario nuevo:** decláralo con el hook; `terminar(true)` lo suelta en el acto, porque `AnimatePresence` lo deja montado mientras termina su salida. Si el formulario sigue abierto tras guardar, su `sucio` debe pasar a falso. Una navegación retenida que se queda sin nada que perder sigue sola: nunca debe perderse un clic.
- **Versión .zip: cerrar apaga.** Con `crearApp({ apagar })` existen `POST /api/pestanas` y `POST /api/pestanas/:id/cerrar` (`backend/pestanas.js`). Con sesión, cada pestaña se registra y en `pagehide` avisa con `fetch` keepalive (`registrarPestana`/`avisarCierrePestana` de `api.js`; `sendBeacon` no manda `Authorization`). Al cerrarse la última con sesión el servidor espera 5 s y apaga; `GET /api/health` cancela la espera, y así F5 no apaga. La de contraseña no cuenta. En el .zip no hay «Cerrar sesión» (`puedeApagar()`) y `beforeunload` siempre pregunta con sesión.
- **Usuarios y permisos por pantalla:** antes de todo, `AuthProvider` (`context/AuthContext.jsx`) muestra `PantallaContrasena` hasta que se entra con **usuario y contraseña** (`ingresar` es asíncrono y llama a `iniciarSesion` de `api.js`). La sesión `{ usuario, nombre, rol, permisos }` vive en `sessionStorage` (`depanas_sesion`) hasta cerrar la pestaña; "Cerrar sesión" vuelve a pedirla. Las reglas viven en **`shared/usuarios.js`** (las usan igual el backend y el frontend; `utils/permisos.js` las reexporta y agrega `puedeAcceder`, `puedeHacer` y `rutaInicio`):
  - **Roles:** el **administrador** (`Cesar_01`, rol `admin`, permisos `['*']`) es único, entra a todas las pantallas (también a las futuras), puede hacer todo y es el único con el **Gestor de usuarios** (`/usuarios`); no se elimina ni se le editan rol, pantallas o funciones. Al crear un usuario se elige un rol de `ROLES_ASIGNABLES`, y cada uno trae sus pantallas y funciones (`PERMISOS_POR_ROL`, `permisosDeRol`): **operador** = todo menos el gestor; **empleado** = Agregar compra y Lista de compras, solo con editar compras (sin Catálogo, sin eliminar compras, sin exportar ni cargar). Elegir el rol en `EditorUsuario` aplica sus permisos; después el administrador los ajusta usuario por usuario. Nadie recibe `/usuarios`. `Marta_02` es operadora.
  - **Pantallas** (`RUTAS_ASIGNABLES`) y **funciones** (`FUNCIONES_POR_PANTALLA`: acciones dentro de una pantalla, p. ej. `compras.eliminar`, `catalogo.agregar`). Una función solo cuenta si el usuario tiene su pantalla. `funcionesEfectivas` calcula las que de verdad tiene; un usuario sin lista (`funciones` NULL, de antes de las funciones) las tiene todas en sus pantallas.
  - En `App.jsx` cada ruta va con `protegida(permiso, elemento)`; el menú y los enlaces se filtran con `tienePermiso`, y los botones de cada acción con `tieneFuncion` (`PantallaMaestra`/`DetalleLista` reciben `puedeEditar`/`puedeEliminar`; `PantallaCatalogo` recibe `acciones`). **Pantalla nueva:** agrégala con `protegida` y su ítem en `navegacion.js`; para poder dársela a otros usuarios, súmala a `RUTAS_ASIGNABLES` (en `shared/usuarios.js`) y a `USUARIOS.pantallas` en `mensajes.js`; si tiene acciones que se puedan quitar, a `FUNCIONES_POR_PANTALLA` y `USUARIOS.funciones`, y decide qué rol las trae.
  - **Requisitos de contraseña:** toda contraseña nueva o cambiada cumple los que configura el administrador en el Gestor de usuarios (`EditorRequisitos`): mínimo de caracteres (4–64) y, si se pide, mayúscula, minúscula, número y carácter especial (`REQUISITOS_INICIALES`: 8 y los cuatro). `revisarContrasena` los muestra en vivo en `EditorUsuario` y `faltaEnContrasena` los valida en los dos modos. Las contraseñas que ya existen siguen sirviendo hasta que se cambien.
  - Usuarios de prueba: `Cesar_01`/`DePanas#2026` y `Marta_02`/`DePanas#2026`. Las bases y navegadores que aún tenían a César con `1234` pasan solos a la nueva (se compara con el hash inicial; si ya la cambió, no se toca). Marta pasa de `5678` a la nueva **una sola vez** por base (ajuste `migracionContrasenaMarta`, `migrarContrasenaMarta` en db.js) o navegador (`depanas_migracion_marta`): se verifica la contraseña, no el hash, porque al entrar el hash se recalcula con otra sal; si ya la cambió, no se toca.
  - **Con servidor la seguridad es real:** `POST /api/sesion` devuelve un `token` (sesiones en memoria, `backend/sesiones.js`: vencen tras 8 h sin uso; 5 contraseñas malas seguidas bloquean a ese usuario 5 min, con 429, también si no existe) y toda la API exige `Authorization: Bearer <token>` (salvo `GET /api/health` y entrar). `app.js` vuelve a leer al usuario en cada pedido y `backend/permisos.js` decide qué pantalla o función pide cada ruta (las mismas reglas de `shared/usuarios.js`; 401 sin sesión, 403 sin permiso). En el frontend, `AuthContext` guarda el token en la sesión, `api.js` lo manda en cada pedido (`fijarTokenSesion`), un 401 dispara `EVENTO_SESION_VENCIDA` (se cierra la sesión con `ACCESO.sesionVencida`) y salir llama a `DELETE /api/sesion`. **Pantalla o ruta nueva:** súmala a `permisos.js`. En **modo local** (sin servidor) sigue siendo solo una barrera de interfaz. Los encabezados (`Header`) llevan solo el título de la pantalla, sin frase debajo.
- **Estilos:** tokens de 3 capas en `src/styles/tokens.css` y un `Componente.module.css` por componente. Los componentes usan solo tokens semánticos (`--color-*`), nunca hex sueltos. Presets de animación (Motion) en `styles/movimiento.js`.
- **UI base:** `src/components/common/` (`Boton`, `Campo`, `Selector`, `Tarjeta`, `Insignia`, `Modal` + `CuerpoModal`/`PieModal`, `EstadoVacio`). Toda pantalla se arma con estas piezas. Hooks en `src/hooks/` y formateo en `src/utils/formato.js`: usa `fechaHoyISO()`, nunca `toISOString()`, que da UTC.
- Cada directorio de `src/` tiene un `README.md` con sus convenciones. Las decisiones técnicas del refactor están en `docs/DECISIONS.md`.
- **Documentación** (índice en `docs/README.md`): `docs/sitio/` es el sitio con la marca (Inicio, Módulos, Arquitectura, Decisiones, Calidad) y `docs/manual/` el manual de uso del cliente (va en el .zip; sus capturas salen de la versión demo). Un módulo, una regla o una decisión nueva actualiza su página del sitio y, si cambia cómo se usa, el manual. Los planes ya ejecutados están en `docs/historial/`.
- **`src/services/api.js` es la única capa de datos** (`fetchListas(filters)`, `guardarLista`, `actualizarLista(id, …)`, `eliminarLista(id)`, `eliminarListas(ids)`, `exportarDB`, `importarDB`, `leerComprasJSON`, `analizarCompras`, `importarCompras(compras, decisiones)`, y de usuarios `iniciarSesion`, `fetchUsuarios`, `crearUsuario`, `editarUsuario(usuario, …)`, `eliminarUsuario`, `fetchRequisitosContrasena`, `guardarRequisitosContrasena`). Tiene **dos modos que nunca se mezclan**, decididos una vez por carga con `detectarModo()` (`GET /api/health`; `main.jsx` la llama al arrancar y, en servidor, espera también el catálogo). Mientras el modo no se conoce, las funciones síncronas del catálogo devuelven listas vacías, nunca los datos locales:
  - **servidor:** todo va a `/api/compras` y los errores del backend se propagan a la UI. Nada se copia a `localStorage`.
  - **local:** sin backend, todo vive en `localStorage` (`depanas_listas`, con `MOCK_LISTAS` de ejemplo; `depanas_usuarios`, con los usuarios iniciales; `depanas_requisitos_contrasena`).
  Los errores de un campo llevan `error.campo` (p. ej. `'usuario'` o `'contrasena'` repetidos) para marcarlo en el formulario.
  No agregues caídas silenciosas a `localStorage` cuando el backend falla. Las páginas nunca usan `fetch` ni `localStorage` directamente.
- **Catálogo:** es la **única fuente de las opciones**; cada compra guardada registra en él su proveedor, materiales, categorías y productos. `getProveedores()`, `getMateriales()`, `getCategorias()`, `getProductos()` y `getAsignacion(material)` son **síncronas** y alimentan `AutocompleteInput` (buscador tipo Excel). En modo servidor leen una caché de `GET /api/catalogo`; en local, `depanas_catalogo` (completo, `version: 2`), que nace del Excel (`CATALOGO` en `api.js`, copia de `backend/db/catalogo.js`) + las compras locales. La pantalla Catálogo usa `fetchCatalogo()` (con `uso`), `agregarAlCatalogo`, `editarEnCatalogo` (renombra también en las compras; en una categoría o un producto acepta `materiales`, la lista completa de los que la llevan) y `eliminarDelCatalogo`. `exportarCompras({ desde, hasta, formato: 'xlsx' | 'json' })` descarga un Excel `.xlsx` real o JSON (armados en `utils/exportar.js`; el `.xlsx` con `write-excel-file`, que se carga solo al exportar). El Excel lleva dos hojas: «Compras» (una fila por artículo) y «Resumen», el **reporte de gastos** del rango (totales, por proveedor, por categoría y por mes), calculado con `shared/gastos.js` (`resumenGastos`, `subtotalCompra`, `totalCompra`). Pruebas de cálculos, filtros y reportes: `backend/test/calculos.test.js` (con `node:test`: cumplen el papel de JUnit, que es de Java) y `frontend/src/utils/exportar.test.js`. No se usa CSV: su separador depende de la configuración regional y Excel lo abría en una sola columna. **Exportar y Cargar por módulo:** Lista de compras los abre desde su menú ⋮ (`/exportar`, `/cargar`); cada sección del Catálogo tiene su propio ⋮ con `exportarCatalogo(tipo, 'xlsx' | 'json', elegidas?)` y `leerCatalogoJSON` + `importarCatalogo(tipo, filas)` (backend: `POST /api/catalogo/:tipo/importar`). Antes de exportar o cargar, `SeleccionCatalogo` deja elegir qué ítems entran (todo elegido al abrir; buscador; «Elegir todos»/«Quitar todos» sobre lo visible; un dato por tipo y, al cargar, «Nuevo»/«Ya existe») y su botón pide la confirmación con la cantidad elegida. Ventana y archivos usan `ordenarFilas` (`shared/catalogo-json.js`): por nombre, y los artículos por categoría (alfabético, sin categoría al final) y luego por nombre. El respaldo `{ tipo, version, filas }` y su validación viven en `shared/catalogo-json.js`; cargar crea lo que falta y actualiza lo que existe, nunca borra, y es todo o nada. Cada material tiene **una categoría y ninguno, uno o varios productos**: los productos van en el mismo campo `producto` como lista «Arepas, Empanadas» (helpers en `shared/productos.js`, usados igual por el backend y `api.js`; por eso un nombre de producto no puede llevar comas), y cada compra guarda todos los productos del artículo. `getAsignacion` devuelve `producto` (texto) y `productos` (lista). **Formulario del artículo en Agregar compra** (`AsignarMaterial`, abierto desde `BloqueCompra`): junto a cada artículo hay un botón: **«+»** con el campo vacío o un artículo no registrado (crea uno con `asignarMaterial(nombre, { categoria, productos, proveedor, nuevo: true })`; 409 con `campo: 'nombre'` si ya existe) y **lápiz** con uno registrado (edita nombre, categoría y productos con `editarEnCatalogo('material', …, { …, proveedor })`, que los propaga a sus compras). Sin `catalogo.editar` (`puedeEditarArticulo`) el lápiz sale apagado y solo se completa lo que le falte: `PUT /api/catalogo/materiales/:nombre` responde 403 si cambia lo ya asignado. Renombrar emite `EVENTO_ARTICULO_RENOMBRADO` (`utils/eventos.js`): lo escuchan las otras compras abiertas y Lista de compras. Guardar pide confirmación con un resumen y avisa con un toast. **El producto es opcional** (en compras, Catálogo y respaldos; la categoría es obligatoria al guardar el formulario): `necesitaAsignacion(material)` solo es verdadero si al artículo le falta algo **y** nunca se ha comprado (`getComprasDeMaterial`). «Ahora no» deja guardar la compra y marca la fila en rojo con un «!» (`marcado` de `Campo`; al reabrir, el formulario dice qué falta); la X o Esc durante un guardado cierran sin guardar. De la segunda compra en adelante no se pide nada ni sale rojo. **Nombres parecidos:** `nombreParecido` (`utils/parecidos.js`, solo en el frontend) advierte con `AvisoDestacado` en el nombre del formulario del artículo, los buscadores de categoría y producto (`SelectorOpciones`), el nombre de `EditorCatalogo` y, al salir del campo, el Proveedor de la compra. Nunca impide guardar. `buscarEnCatalogo` (db.js) compara también en JavaScript porque `COLLATE NOCASE` solo ignora mayúsculas ASCII (`AZÚCAR` y `Azúcar` son el mismo registro; `Azucar` es otro, y sale la advertencia). `totalLista(lista)` suma los montos. **Ficha del proveedor** (ubicación, varios teléfonos, contactos con nombre y teléfono): columna `ficha` (JSON) del catálogo en el backend y `fichas` en el catálogo local; `GET /api/catalogo` la devuelve en `fichas` (claves en minúsculas) y `agregarAlCatalogo`/`editarEnCatalogo('proveedor', …)` aceptan `ficha`. Se valida con `shared/proveedores.js` en los dos lados; los errores llevan `campo` (`telefono-<i>`, `contacto-<i>`…). Se edita en `FichaProveedor`, dentro de `EditorCatalogo`. **Proveedores de cada categoría:** una categoría guarda los proveedores que la surten (varios; un proveedor puede surtir varias). `GET /api/catalogo` los da en `proveedoresPorCategoria` (claves en minúsculas; en local, el mismo campo de `depanas_catalogo`) y `agregarAlCatalogo`/`editarEnCatalogo('categoria', …)` aceptan `proveedores` (la lista completa; error con `campo: 'proveedores'` si uno no existe). En Agregar compra, `getMaterialesPorProveedor(proveedor)` (síncrona, igual en los dos modos) sugiere solo los artículos de las categorías del proveedor (`getCategoriasDeProveedor`) y, si no surte ninguna, todos; siempre ordenados con «Materia Prima» primero. Cada compra guardada o importada liga su proveedor con la categoría de cada artículo, y `asignarMaterial(material, { categoria, productos, proveedor })` liga la categoría elegida con el proveedor de la compra (`AsignarMaterial` muestra primero las categorías del proveedor). El respaldo de categorías lleva `proveedores` (opcional; al cargar se suman y los que no existen se omiten).
- Las notificaciones usan `useToast().addToast(message, 'success' | 'error')` de `src/context/ToastContext.jsx`. **Todo botón de acción** (guardar, cancelar o descartar con datos, eliminar, cargar, descargar, cerrar sesión) se confirma antes con `ConfirmDialog` (`components/common`), con los textos de `COMPRA` y `CONFIRMAR` en `mensajes.js`; navegar o abrir una ventana no se confirma. **Todos los textos que el sistema le dice al usuario** (toasts, errores, validaciones, estados vacíos, acceso) viven en `src/utils/mensajes.js`, con la voz de marca; los tests los importan de ahí.
- **Material = artículo:** en toda la interfaz (textos, columnas, rutas como `/catalogo/articulos`, mensajes de error) se dice **artículo**; el código, la API, la base y los JSON de respaldo siguen usando `material` para no romper respaldos ni el trabajo del equipo. `/catalogo/materiales` redirige a `/catalogo/articulos`.
- **Agregar compra por pasos (`BloqueCompra`, solo en una compra nueva):** primero se ven fecha y proveedor; con proveedor, la primera fila; con una fila completa (artículo, cantidad, unidad y monto), la fila fantasma «Agregar otro artículo» al final de la tabla (`COMPRA.agregarFila`, solo si la última fila está completa), subtotal, IVA, total, Guardar, Cancelar y «Nueva compra». Lo que aún no toca no se muestra (nada apagado en gris). Una compra extra vacía muestra solo Cancelar para quitarla. Al editar una compra guardada se ve todo. Esta regla por ahora es solo de Agregar compra.
- **Fila de una compra (`BloqueCompra`):** Monto y Precio unitario se pueden escribir; al cambiar la cantidad se conserva el último escrito y se recalcula el otro. El monto escrito se guarda exacto y el precio interno lleva 4 decimales. El precio de la última compra se pone solo, sin mensaje, y nunca reemplaza lo escrito a mano. El botón «+» de cada artículo siempre se ve: activo con un artículo nuevo o incompleto, apagado si está vacío o completo. «Categoría · Producto» va como `title` y texto `solo-lector`. `COMPRA.confirmarGuardar.mensaje` devuelve partes `[{ texto, negrita }]` porque `mensajes.js` no lleva JSX. «Agregar teléfono» (`FichaProveedor`) se apaga mientras haya un teléfono vacío.
- **Modelo: compra (lista)** `{ id, origen_id?, proveedor, fecha, categoria, materiales: [{ material, cantidad, unidad, monto, categoria, producto }] }`. `fecha` es ISO `YYYY-MM-DD`. `monto` es el **total de la línea** (no unitario); el gasto de la compra es la suma. `categoria` y `producto` de cada material salen de su asignación en el catálogo. El filtro `material` devuelve las compras que contienen ese material. En modo servidor el `id` es un UUID (`compra_id`); en local, un número.
- **Modelo: usuario** `{ usuario, nombre, rol: 'admin' | 'operador' | 'empleado', permisos: [rutas], funciones: [ids] }` (la API y `api.js` devuelven las funciones efectivas; el administrador, `['*']`). La contraseña nunca sale de `api.js`/backend: se guarda como hash PBKDF2-SHA256 `pbkdf2$<iteraciones>$<sal>$<hash>` con **600 000 iteraciones** (backend en `contrasenas.js`, local con WebCrypto; mismo formato); un hash con menos iteraciones se recalcula al entrar. Las contraseñas **no se comparan con las de los demás usuarios**: eso le revelaría a quien crea un usuario la contraseña de otro. No se repite el usuario (sin distinguir mayúsculas).
- **Backend, capa DAO:** ninguna ruta escribe SQL. `backend/dao/` tiene un DAO por entidad (`compras.js`, `ingresos.js`, `catalogo.js`, `usuarios.js`) que valida, escribe en transacción y lanza `ErrorDatos` (`dao/errores.js`: 400/403/404/409, con `campo`); las rutas solo traducen HTTP ↔ DAO con `routes/responder.js`, que responde el `ErrorDatos` o, ante un error inesperado, lo registra y devuelve un 500 genérico sin detalles internos. Modelo de datos, motor (SQLite con `node:sqlite`) y por qué: `docs/MODELO_DATOS.md`. **Ruta o dato nuevo:** su SQL va en el DAO, no en la ruta.
- **Backend:** tabla `ingresos` (una fila por material) con `compra_id` para agrupar cada compra, `unidad` y la `categoria` de cada fila; tabla `catalogo` (opciones de los desplegables y categoría/producto de cada material) sembrada desde `db/catalogo.js` (las listas de `Datos De Panas.xlsx` y, en `proveedorCategoria`, qué categorías surte cada proveedor según sus filas; copia en `CATALOGO` de `api.js`) y completada con lo que ya hay en las compras **una sola vez por base** (`PRAGMA user_version`), para que lo eliminado no reaparezca; tabla `proveedor_categoria` (por `id` del catálogo, `ON DELETE CASCADE` con `PRAGMA foreign_keys = ON`: renombrar no la toca y eliminar la limpia), llenada una vez con las compras existentes (`user_version` 2). `registrarCompra` (db.js) agrega al catálogo lo de cada compra guardada o importada y liga su proveedor con la categoría de cada artículo (`vincularProveedorCategoria`). `/api/catalogo` (routes/catalogo.js) agrega, renombra (también en `ingresos`) y elimina. Tabla `usuarios` (contraseña con hash, `permisos` y `funciones` en JSON, `rol` admin/operador/empleado) sembrada desde `db/usuarios.js` solo si está vacía (el administrador no se elimina, así que nunca vuelve a sembrarse); las bases con la tabla anterior (sin `empleado` en el CHECK ni `funciones`) se rehacen al abrirlas (`migrarUsuarios` en db.js). Tabla `ajustes` (clave → JSON) guarda los requisitos de contraseña. `routes/usuarios.js` da `POST /api/sesion`, `/api/usuarios` (GET, POST, PUT `/:usuario`, DELETE `/:usuario`) y `GET/PUT /api/requisitos-contrasena`, con las mismas reglas que el modo local. `db.js` migra bases del esquema anterior al abrirlas. `/api/compras` (routes/listas.js) trabaja con compras completas y valida montos y cantidades > 0; `POST /api/compras/eliminar` `{ ids }` (función `compras.eliminar`, ids validados con `shared/lote.js`) elimina varias en transacción; una ruta de `/api` que no existe responde 404 en JSON; `/api/ingresos` da acceso fila por fila. **Conexión SQLite** (db.js): modo WAL con `busy_timeout` de 5 s; `consolidar()` pasa el WAL a `depanas.db` al abrir (TRUNCATE) y tras cada escritura exitosa (middleware en app.js), e `index.js` cierra la conexión con Ctrl+C. Así una copia a mano de solo `depanas.db` siempre está completa. `/api/ingresos` valida con `validarCompra` igual que `/api/compras`. Exportar usa `VACUUM INTO` (con WAL, copiar el `.db` a pelo exportaba una base vacía); importar un `.db` valida el archivo y guarda `depanas.respaldo.db`. **Cargar JSON** (`POST /api/db/importar-json` con `{ compras, decisiones }`): la validación y el análisis viven en `shared/` (`compras-json.js` recorta los textos y valida; `carga-compras.js` compara) y los usan igual `api.js` y el backend. Cada compra es nueva, duplicada (se omite) o modificada (pide una decisión por índices de filas; si la compra guardada cambió, 409). La identidad es `origen_id` (columna de `ingresos`, se conserva al editar y reexportar) o, si falta, `id`; `ingresos.compra_categoria` guarda la categoría de la compra aparte de la de cada material.

## Diseño (obligatorio)

`DESIGN_DECISIONS.md` (raíz) describe la marca **tal como vive hoy en el sitio** (nació del *Brandbook DE PANAS, mayo 2026*; lo que se aparta está en su sección «Diferencias con el brandbook») y **toda pantalla nueva debe seguirlo**. Precedencia: **`DESIGN_DECISIONS.md` (sitio actual) > brandbook > skills de `.claude/skills/`**; la skill `brand` es su resumen operativo. `apple-design` guía proporciones, interacción, animaciones y materiales; `ui-ux-pro-max`, `brand` y `design-system` guían tokens, accesibilidad y UX. Lo esencial:

- Paleta: Rojo Vinotinto `#911C0D`, Naranja Sazón `#EF7D05`, Amarillo Criollo `#F8A914`, Verde Fresco `#6DAD28`, Verde Ávila `#144428`, Crema y Trigo `#FEEECC`. Sin negro puro. Naranja y crema son los protagonistas (sidebar, barra inferior y botón primario en naranja). Texto sobre naranja: siempre `--color-on-primary` (Ávila profundo `#0F331E`, 5.03:1); nunca texto blanco o crema sobre naranja, amarillo o verde fresco (el logotipo tipográfico está exento).
- Tipografía: Josefin Sans para titulares e interfaz (titulares en mayúsculas) y Cardo para textos extensos.
- Las tablas van sobrias, con los montos alineados a la derecha. Contraste WCAG AA en todo.
- Movimiento: feedback al presionar, springs interrumpibles para lo arrastrable y `prefers-reduced-motion` siempre respetado.
- Assets de marca en `frontend/public/brand/` (logo, `arepa.png` para el menú, el collage `patron-elementos-graficos.webp` y los íconos de favicon/PWA, conectados en `index.html` y `public/site.webmanifest`).
- Fondo: el collage de la pág. 10 del brandbook va en `body::before` al 10 % (tokens `--patron-*`). Una pantalla con fondo crema no pinta su propio `background`. El texto directo sobre el collage usa `--color-text`, nunca `--color-text-muted` (no llega a AA sobre los trazos).
- Header: transparente arriba, crema sólido con sombra al hacer scroll, sin `backdrop-filter`.
- **Vista de teléfono por debajo de 1100 px** (`@media (max-width: 1099px)`; lo solo de escritorio, `(min-width: 1100px)`; `ToastContext` usa la misma consulta): barra inferior en vez de menú lateral y tablas como tarjetas. Va en 1100 y no en 768 porque con el menú lateral las tablas se cortaban antes (lo primero, Categorías del Catálogo a ~1024 px); ver el comentario en `styles/base.css`. Ningún botón puede quedar cortado a ningún ancho: lo vigila `e2e/navegacion.spec.js` (de 1280 a 320 px). Una acción que no cabe baja de línea (`Tarjeta` deja que su `accion` se acomode en varias líneas).
- Textos para el usuario: siempre desde `src/utils/mensajes.js` (voz de marca de la diapositiva 10; errores y validaciones sin modismos).

Las skills del proyecto (diseño, frontend, backend y base de datos, pruebas, seguridad y las lentes de auditoría con `full-audit`) están listadas en `.claude/skills/README.md`; antes de tocar el backend usa `backend-sqlite` y ante cambios de sesión, permisos o archivos, `revision-seguridad`. Los reportes de auditoría van en `docs/revisiones/`. Las skills ejecutan scripts desde la raíz del repo, p. ej. `python .claude/skills/ui-ux-pro-max/scripts/search.py "<consulta>" --domain ux`.

## Convenciones

- El código, los nombres (componentes, funciones, variables) y los textos de la UI están en **español**.
- Un cambio en los datos toca los dos modos de `src/services/api.js` y el backend, con tests en `frontend/src/services/api.test.js` (modo servidor con `fetch` simulado y modo local) y en `backend/test/`.
